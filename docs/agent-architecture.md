# Agent 架构与运维

## 工作流与模块边界

订阅助手和论文助手共用持久会话、租约、取消、幂等、权限与凭据校验。订阅助手仍使用受限 JSON 动作协议，草案只有用户确认后才创建订阅。

论文助手采用 `paper-fixed-v5` 固定工作流，模型不能选择工具或规划步骤：

- 报告：Paper Context → 版本化全文 → 固定任务 → 问题、方法、实验、结果、局限五次分析 → 一次语义校验 → 服务端结构化输出。
- 超出 64 KiB 单次序列化输入时，系统按原文顺序分批，每批一次提取五类候选证据，再执行五次分析和一次校验；N 个批次共 N＋6 次调用。所有提取文本包括附录均处理，正文和证据不静默截断。汇总仍超限则明确失败。
- 追问：一次问题/指代规范化和英文关键词生成 → 系统限定单文档 BM25 检索 → 一次回答 → 一次校验。历史帮助理解指代，不替代原文证据。

`internal/agent` 编排上述流程和证据校验；`internal/document` 管理版本化文档、页序、章节位置和检索；`internal/platform/document` 实现 arXiv 下载、Poppler 及可注入 OCR 接口。业务层不构造数据库或外部客户端，启动层负责装配。API 只提交/读取，Worker 执行；普通邮件不等待论文任务。

## 文档与依据范围

Worker 安装 Poppler 的 `pdftotext`、`pdfinfo`、`pdfimages` 和 util-linux 的 `prlimit`。本期不安装或接入 OCR 服务。文本解析失败可调用预留 OCR 接口；未配置时明确报告失败原因，并自动生成摘要版。空白且无栅格图像的页保留；文字稀少且包含图像的页保守视为需要 OCR，避免混合 PDF 被误判为完整全文。

解析器 `poppler-reading-order-v3` 使用 Poppler 默认阅读顺序（不使用保留物理版式的 `-layout`），避免双栏正文在后续空白归一化时逐行交错。在归一化空白之前识别编号标题和常见章节名，保存页码与行号。识别失败不删除文本或阻断分析。文档记录实际页数（包括尾部空白页）、章节和文字完整性。缓存身份包含解析器版本，旧缓存不复用。

PDF 只从校验后的 arXiv 标识构造固定版本地址，不接受客户端 URL，禁止重定向，共用 arXiv 限速器。历史无版本链接先核对元数据更新时间。最大 25 MiB、200 页、4 MiB 文字；子进程限制 512 MiB 地址空间、25 秒 CPU、30 秒墙钟及文件资源。临时文件清理，不提供 PDF 镜像。

分页分段仍为最多 600 词、重叠 80 词。完整覆盖仅表示所有提取文本进入分析，不表示图像、公式和复杂表格被可靠理解。

下载失败、扫描页、解析失败或文档准备超过 105 秒时自动使用摘要，持久化 `effective_context_mode` 与 `fallback_reason`。模型失败、校验失败、版本冲突、预算耗尽不触发摘要降级。摘要版追问维持摘要依据；用户重新生成全文报告可再次准备全文。

## 证据与输出

内部分析返回状态及逐条论断，每条论断的证据只返回 `{ "id": "服务端提供的片段编号" }`。`internal/document.Passages` 将检索分段继续按最多 1000 UTF-8 字节划分，优先词边界，保存起止字节位置；所有字节均保留，编号包含原分段及起始位置。标题/摘要同样分段。模型选择本次输入中的编号，服务端从固定文档取出整段原文、页码、链接及哈希；模型不生成或改写引文。批次提取采用同一协议，汇总保留原编号，追问仅开放被检索分段中的片段。

确定性校验拒绝未知字段、重复 JSON 键、额外数据、本次输入之外的编号、同一论断重复引用和超长输出。有效编号只说明出处存在，不证明论断正确。最后一次模型调用读取论断和被引用的原文片段（去重传入，论断只携带编号），逐项判断是否支持，不能补写事实。实验数值、比较条件、过度推测和作者未说明的局限都属于校验范围。没有模糊匹配、清洗 JSON、自动修补引文或失败重试。

不受支持的论断被删除；缺失信息返回“论文未明确说明”；没有可靠证据返回“当前材料不足以可靠回答”。摘要版明确说明缺失判断只针对当前材料。语义校验降低风险，但不保证所有事实完全正确。

消息 `result.report` 只含 `problem/method/experiments/results/limitations` 五个字符串。`result.fields` 保存状态与引用 ID，旁侧保存依据模式、降级原因、覆盖范围和论文/文档/工作流版本。`content` 是服务端统一生成的 Markdown；页码、引用 URL 与哈希也由服务端确定。历史消息没有 `result` 时按原格式展示。

## 接口、运行与恢复

继续使用 `/api/v2/agent/conversations/{id}/messages`：论文请求增加 `task=paper_report|paper_followup`。报告忽略问题文本并使用固定目标；省略任务类型的旧论文请求视为追问，同样需要当前会话已有当前论文版本的成功报告，否则返回 HTTP 409 `PAPER_REPORT_REQUIRED`。会话响应 `paper_report_ready` 告知前端是否解锁追问；后端在提交事务及 Worker 执行前均校验，报告查询不受消息分页或历史上下文截断影响。订阅请求不接受论文任务类型。运行响应公开阶段、批次进度与实际依据模式。

| 工作流 | 模型调用上限 | 时间上限 |
| --- | ---: | ---: |
| 论文报告 | 24（最多 18 批提取＋6） | 15 分钟 |
| 论文追问 | 3 | 180 秒 |
| 订阅助手 | 4，另限 3 次工具执行 | 180 秒 |

单次供应商调用仍最多 30 秒、输出上限 4096 token。统一 CallRunner 管理凭据、并发、冷却和日限额。报告与追问共用 `paper_qa` / `AI_PAPER_QA_DAILY_LIMIT`，按实际供应商调用计数。日志与步骤保存 call_id、阶段、token、耗时和错误码，不保存密钥或隐藏推理。校验错误分别使用 `output_invalid_json`、`output_language_mismatch`、`output_schema_mismatch`、`output_limit_exceeded`、`evidence_id_unknown`、`review_incomplete`（历史 `evidence_quote_mismatch`、`evidence_quote_length` 继续展示）；调用日志额外保存服务端构造的 JSON 字段路径，不记录模型原始响应。前端通过已有 steps 接口展示失败步骤、原因代码和诊断编号，调用历史使用相同的原因说明。

每会话最多一个活动任务；`(conversation_id,idempotency_key)` 去重，任务参数参与请求哈希。30 秒租约每 2 秒续租，epoch 拒绝旧执行者写回。调用前保存 `calling`，返回通过协议校验后原子保存阶段输出与调用步骤。恢复重用已保存阶段；发现 `calling` 标记结果未知，不自动重复付费调用。任何校验未完成的报告均不发布。

写入最终消息时在事务中再次检查论文元数据快照、文档版本、用户访问权、凭据版本和运行截止时间，空引用报告也不能绕过版本检查。取消与删除会话沿用已有锁和级联语义。

具名凭据沿用迁移 00029 的身份约束：`credential_id` 绑定 generation/version，切换聊天模型不改变邮件默认条目，不退回同供应商其他 Key。旧省略身份请求仅在供应商凭据唯一时兼容。配置变更中止正在使用旧版本的任务。

## 升级与验收

1. 停止 API 与 Worker，备份数据库和 AI 主密钥。
2. 在隔离环境验证迁移 00030 和检查脚本，再在目标环境应用迁移。迁移明确终止旧版未完成论文任务并释放会话，保留历史消息；订阅工作流不受影响。
3. 同步发布 API、Worker 和构建后的前端，刷新浏览器。不要混用新旧服务。当前工作流 v5 与解析器 v3 的修复不需要新迁移：解析器身份变化自动绕开旧缓存；未完成的 v1/v2/v3/v4 工作流由执行器拒绝，未知调用仍不重放。v1/v2/v3/v4 已完成报告继续保留且可用于追问前置判断，追问重新读取当前解析器原文。
4. 验收报告、证据、摘要降级、追问、取消与刷新恢复，回归订阅草案、普通邮件和旧摘要。

运行 `scripts/verify.sh` 与 `scripts/test-migrations.sh`，测试必须使用 `_test` 库、隔离 Redis/Mailpit。真实模型评测与人工论断审阅独立进行，见 `evals/agent/README.md`；确定性测试成功率不代表模型准确率。回退使用验证过的备份，不对业务库执行破坏性 Down。

## 固定报告语言约束（工作流 v5）

用户报告 `problem`、`limitations` 整段英文，而其他字段为中文。五项分析各自调用模型，旧版共用一条“报告中文、追问按用户语言”的提示；结构与事实校验均不验证叙述语言，因此模型没有遵守中文要求时仍可发布。这与英文缩写、公式和原文引用的保留不同。

v5 为报告/追问使用独立语言策略，每项报告输入明确携带 `output_language=zh-CN`，系统要求每条 `claims[].text` 使用简体中文，一般术语翻译为中文，模型/数据集名称、缩写、变量和单位可保留原文。JSON 字段、状态和证据编号不翻译。追问携带原问题 `original_question`，按原问题语言回答，避免规范化问题或历史中文报告改变回答语言。

报告解码增加保守的文字检查：每条论断必须含汉字，否则返回 `output_language_mismatch` 与 `$.claims[i].text` / `chinese_text_required`。这不是完整语言识别，不能证明混合句子的每个词均符合中文表达，也不声称能区分所有使用汉字的语言；它明确阻止本次整条英文的问题，同时容许中文技术描述保留英文专名。证据不参加语言检查、不翻译，仍由服务端从当前文档原样取出。英文追问不受该报告检查约束。

校验失败按已有流程保存诊断并终止，不发布混合语言的部分报告，不增加翻译调用或自动重试；短报告仍为六次调用。旧 v4 检查点不继续执行，避免复用未检查语言的步骤；已完成 v1–v4 报告和历史继续读取，只有用户手动重新生成才应用当前规则。无需新增迁移，部署需同步 API/Worker 和前端。

本轮使用用户给出的英文问题/局限文字做确定性回归，检查含英文缩写与公式的中文论断、英文证据保留、英文追问解码兼容，以及第二条英文论断导致整轮失败且不重试。未进行新的真实供应商调用，不把这组测试视为模型后续必定遵守语言要求的证明。
